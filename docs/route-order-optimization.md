# Reorder a visitor's complete selection

The **Reduce detours** action in My itinerary and the tour launch panel opens a read-only preview. Every selected attraction is retained; only its order changes. The first stop is fixed by default, and the visitor can independently lock the last stop or free both endpoints. The comparison includes the original and proposed walking maps, distance, walking time, total time and the new ordered stop list. Applying updates the browser draft, map markers and subsequent tour session order. Undo restores the previous draft order and preset route ID. It does not rewrite saved recommended routes or active tours.

`POST /tour-experience/optimize-order` accepts the same pace, gate, steps and reserve options as the existing route preview, plus `fixed_start` and `fixed_end`. It validates 2–20 unique, available attractions in one city. All distances and both returned geometries come from the existing pedestrian graph, without straight-line fallbacks. Visits, breaks, walking and optional gate legs use `route_overview` unchanged.

Up to 16 movable stops use exact subset dynamic programming, minimizing rounded network metres with walking minutes as the tie breaker. The 16-attraction Summer Palace catalog therefore supports exact ordering with any endpoint settings. Larger selections use bounded deterministic multistart nearest-neighbour and 2-opt improvement and never claim global optimality. The original order is retained on an equal-cost result, an increase in total time or a failure to improve. An unavailable walking path fails explicitly. Changes to the graph during calculation invalidate the response.

The frontend cancels and invalidates proposals when selected IDs, pace or endpoint settings change. A late result cannot replace a newer calculation. Apply checks the input selection, exact membership, locked endpoints and non-increasing costs before emitting the new order. No tour, route or other database row is written by this endpoint.

Validation: exhaustive permutations for small routes and all endpoint combinations; gate costs; full 16-stop selection and idempotence; bounded 20-stop results; disconnected/invalid selections; changed networks; read-only API calls; frontend preview/apply, cancellation, retry and stale-request races. Actual local data with all 16 stops, fixed first stop and free last stop changed from **15,437 m / 373 min** to **6,800 m / 248 min**, including the same 132 minutes of visits. This is a comparison for that selection and map snapshot, not a promise of live travel time.
