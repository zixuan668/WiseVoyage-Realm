# 景点知识与数字人问答维护

本轮补全北京颐和园16个已有景点，不新增点位、不重排游客路线。
每处有概览、历史、建筑与空间、现场看点、拍照、亲子、通行、易混淆问题、位置、时长、季节、设施、开放、游船、口语讲解与专题问答。
129条问答包含可核实事实与明确标注的编辑建议；没有核实的设施位置和实时运营状态不会补写。

## 资料与更新

- 编辑来源和讲解：`scripts/build_summer_palace_knowledge.py`。机构来源、核对日期与传说证据性质一起维护。
- 构建结构化档案与16份Markdown：`python scripts/build_summer_palace_knowledge.py`。
- 应用到当前数据库：`python scripts/sync_summer_palace_knowledge.py`。
- 同步前自动将受影响记录备份到忽略目录 `work_dirs/knowledge-backup-*.json`。只更新知识字段和知识文档记录，保留景点ID、坐标、图片、路线、账号和历史会话。
- 运行中的后端重启后加载新资料；知识索引默认使用轻量检索，不需要GPU。此次索引21份文档、317个分块。
- 结构化档案在 `data/summer_palace_knowledge.json`；可读档案在 `static/tour_files/knowledge_base/dossiers/`。

历史描述重新组织自北京市公园管理中心、园林绿化局、文物局、颐和园官网、北京旅游网、故宫研究与UNESCO资料。
每份档案附具体链接，不能将摄影建议、传说或策展时长称为经过测量的历史事实。
服务设施仍需后续现场核验；最新门票、闭园、临时施工、船线、演出、天气、人流没有接入实时数据。

## 回答行为

`tour_dialogue.py`先识别问什么，再解析追问，向模型提供对应资料与任务。
设施、位置、下一站、时长、开放/游船的未知状态按确定性事实回答，避免模型虚构。
普通问题先回答重点，要求详细才展开；“继续讲”“一句话说重点”等沿用最近话题。
显式提到其他景点时回答那个景点，不推进游览路线；后续指代可延续这个对象。
实际切换站点后清除旧景点话题，保留游客明确表达的同行与体力需求。
路线推荐不因聊天自动变更。问题含多个主题时保留各主题，比较景点时分别给出依据。

检索按景点和话题过滤，Markdown以显式标记分块，禁止跨景点拼接。
没有匹配的资料不强取排名第一的无关段落。模型不可用时用详细本地档案回答，并记录降级原因。
模型密钥校验不会把非ASCII占位文字当成有效凭据；模型请求有超时，日志不记录完整提示词。

显示文字与 `spokenText` 分开：详细文字留在对话区，语音最多6句、460字符，清理Markdown与网址。
星云数字人与Edge-TTS都采用同一口语文本；没有添加用户已删除的暂停、继续、重播讲解按钮。
Edge-TTS的语速按实际倍率计算，请求限时；可通过 `EDGE_TTS_PROXY` 配置仅用于语音的代理，不改全局网络设置。

来源与意图保存在每条导游消息的 `answer_metadata`，页面刷新仍可展开参考资料。
对话记忆独立存放在会话 `dialogue_context`，不覆盖个性化路线偏好。

## 验证

```text
python -m unittest discover -s scripts/tests
python scripts/verify_tour_dialogue.py --http
cd frontend
npm run test:unit -- --run
npm run build-only
```

数据库验收脚本创建一个标注为“知识问答验收”的新会话，完成后结束；不修改已有游客会话。
其中11个数据库场景屏蔽远程模型和TTS，验证离线降级路径；`--http`另测一个真实模型/语音接口。
真实模型输出需持续人工检查，规则与提示词不能保证每个开放问题都完全准确。
全项目类型检查仍有既存错误，位于旧直播组件和数字人编辑页；本次导览、来源链接和API类型没有新增类型错误。
