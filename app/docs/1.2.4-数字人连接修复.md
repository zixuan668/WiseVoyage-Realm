# 1.2.4：Android 数字人连接兼容修复

基准：main `d31183cf5bd3ca9948d1c7fbf85b091a91368ee8`，叠加本次 App 修复；不修改 Web 和后端。

## 问题和修改

1. main 中的 App 直接加载官方在线 `@latest` SDK。当前该文件与官方 2.4.1 npm 包内容一致，Android 环境会强制要求软件解码声明；即使硬件解码已实际输出视频帧，仍可能拒绝初始化，尚未向后端发起数字人会话就显示连接失败。
2. 将固定版本的兼容 SDK 随 App 打包。保留实际帧解码、安全上下文、WebGL、音频等检查；去掉强制软件解码的限制，导览与聊天语音明确请求硬件解码。
3. 两个入口共用一次 SDK 加载，避免重复请求；加载失败可重试，并提供中英文提示。后端凭据依然只保留在服务器。

## 验证与边界

- 原官方文件在“已有硬件解码帧”的测试中失败，修复后通过；真实解码失败仍会返回失败。
- `node --test app/tests/xingyun-sdk.test.cjs`：5 项通过，包括共享加载、失败重试、导览及聊天语音初始化与错误传递。
- Chrome 使用 Android User-Agent 加载实际打包 SDK，构造函数可用、两个调用仅请求一次 SDK、无未捕获脚本错误。此项没有验证实际 Android 设备。
- 现有后端真实创建独立匿名测试导览，连接数字人云端约 4.5 秒返回 `error_code=0`、会话及资源包；云端会话和测试导览随后关闭。没有使用用户正在进行的导览会话。
- 生成新 APK 后另行检查签名、包名、实际桌面名称、版本码、编译资源与包内资源一致性，并记录在忽略的 `app/unpackage/releases/1.2.4/`。
- 尚未连接 Android 真机，不把解码模拟测试或云端资源返回视为用户手机已经恢复。旧 1.2.3 不含本修复，需要安装新包再复测。
